# Agricultural Operations Platform — GitHub requirements reconciliation

**Draft comparison date:** 16 November 2026  
**Repository:** [`SandaruWithanage/agri-operations-platform`](https://github.com/SandaruWithanage/agri-operations-platform), `main` (read-only inspection via connected GitHub account)  
**Owner-decision baseline:** [71-question provisional decision register](AGRI_71_PROVISIONAL_DECISION_REGISTER.md)  
**Authority:** developer-side review only, **not** client-approved requirements, ADR acceptance, a changed codebase, or an instruction to deploy.  
**Repository mutations:** **none**. Nothing in this report represents a merged PR, changed issue, role grant, implemented feature or completed security gate.

## Executive finding

The discussion supplied 71 owner decisions, including substantial **first-release scope expansion** (full GIS, walk-the-boundary GPS mapping and comprehensive reporting), a **different offline-enrollment dependency**, and new offline-device/session/security and hosting rules. Repository documents currently describe a narrower pilot and several provisional designs. The correct next action is **controlled reconciliation**, not bulk replacement of existing approved architecture or silent activation of new workflows.

Severity below means **priority for requirements/design reconciliation**, not a claim that a vulnerability exists in deployed production. **Critical** = blocking design/approval conflict; **High** = substantive first-release scope or contract/security change; **Medium** = needed baseline consistency or operational decision.

## 2. Particularly important things that are NOT conflicts

- **Accepted data/state architecture remains authoritative:** [PostgreSQL/PostGIS + TanStack Query online + Zustand non-sensitive UI + encrypted Dexie field queue; optional Redis](https://github.com/SandaruWithanage/agri-operations-platform/blob/main/docs/architecture/decisions/ADR-data-state-cache.md). Q48 full GIS and Q3 dependency must extend it, not replace its owners or introduce a parallel sync database.
- **GPS legal limitations remain correct:** Even with full GIS, a measured phone GPS polygon is **not** proof of title or an official survey. Keep source, accuracy, verification and dispute status.
- **Existing encryption/auth controls are not automatically superseded:** Owner risk-based MFA, seven-day offline duration and BYOD approval require reviewed design/config changes, not disabling existing conservative guards.
- **ADR 0021 stays NOT Accepted:** Sections 9–10 require A1 client confirmation, A2 independent design security review, A3 prerequisite ADR designs, A4 reviewed owner acceptance change, then OFF-04A–D staged work and a **separate real-officer enablement gate E**. No GitHub changes or authorizations occur from this report.
- **Pilot enrollment decisions are still provisional:** selecting project-specific policy and new cycles does not mean the `operations.enrollment` schema or BFF/UI currently implements those features.

## 3. Decisions still missing from the customer, despite completion of Q1–Q71

1. **DEC-01:** actual registered entity, legal operator/controller/processor roles, name/branding, client decision authority and named approvers.
2. **DEC-10 source verification:** whether the 2026/27 plan's **2,760 or 2,700** count is authoritative, with signed correction/source provenance.
3. **Exact acceptance parameters:** authorized officials, role/permission/scope matrix, real officer-device list and Android/browser support, GPS accuracy threshold, accepted survey-source hierarchy and parcel-overlap tolerance; wording for Sinhala notices and privacy retention.
4. **Real-world evidence:** successful device lock/unlock/revoke/clock-handling and foreground walking GPS; offline GIS tile license and caching rights; independent crypto/ABAC/ADR review; restore tests proving RPO/RTO.
5. **Commercial baseline:** customer-approved first-release scope, timeline, LKR module-level price breakdown, developer-operated hosting fees, support SLA, exit policy, training sessions and signatures. Original LKR 200,000–400,000 planning expectation is **not** proof the expanded scope is feasible for that price.

## 5. Recommended change-control labels

- **Owner-proposed:** chosen in the 71-question conversation; awaiting client confirmation.
- **Client-approved:** confirmed by named authorized client approver, date and written evidence (not yet the case).
- **Architecture accepted:** decision explicitly Accepted by the relevant technical ADR approval process, independent from client business approval.
- **Implemented and tested:** linked code, migration and automated test evidence; does not imply operational readiness.
- **Pilot enabled:** explicit feature-flag/permission/device security enablement after approval and deployment gates (not the case for offline enrollment).
- **Deferred/excluded:** never silently remove from selected first release; a documented approved change request is required.
