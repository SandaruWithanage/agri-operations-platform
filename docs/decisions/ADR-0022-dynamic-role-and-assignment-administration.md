# ADR 0022 — Dynamic role, permission and assignment administration (PROPOSED design, not implemented)

Status: **design proposal for owner and independent security review (Gate G1). No code, migration, grant or role accompanies it.** It covers the IAM-01/IAM-02 part of the owner's staff Phase 1 guide (P1-03, owner decisions Q61–Q66). Those owner decisions are provisional and not client-approved; the client permission matrix (DEC-02) is still unknown, so nothing here fixes role names, counts or risk assignments. Implementation of any migration that creates, changes or materializes privileged grants waits for the review in section 10.

## Context (what exists today)

- Authority is evaluated by `authz.allowed` (farmer/land geography scope), `authz.allowed_project_geography` (project scope) and `operations.allowed_organization` (organization catalog/enrollment-policy scope). Each reads grant rows directly: `authz.permission_grant` (permission text, coverage `organization|assigned`, optional geography/unit, optional registration source, validity window, active flag), `authz.assignment`, `authz.project_permission_grant` and `authz.project_assignment`, always for the signed transaction actor and re-checked after lock waits.
- There is **no role concept**: grants are inserted directly by an operator. There is no person/account separation for staff, no catalog of permission names, no approval workflow, no grant administration API or UI, and no audit of grant changes beyond the rows themselves.
- Runtime identities are restricted logins; privileged work is done by `NOLOGIN` function owners with fixed `SECURITY DEFINER` functions, an HMAC idempotency journal and atomic audit (pattern used for enrollment and policy administration).

## Decision (proposed)

### 1. Roles are data that compile into the existing grants (no rewrite of the predicates)

Introduce configurable roles and bindings, but **materialize** an active binding into ordinary `authz.permission_grant` / `project_permission_grant` / assignment rows tagged with `origin='role_binding'` and the binding id. The three existing predicates, every RLS policy and every existing test keep working unchanged; direct grants stay valid with `origin='direct'` (legacy). Materialized rows are written only by the IAM function owner; revoking, expiring or version-moving a binding sets `active=false`/`expires_at` on exactly its rows, never deletes them, so history stays queryable.

### 2. Data model (additive; every table versioned where mutable)

| Table                                    | Purpose and constraints                                                                                                                                                                                                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `iam.permission_catalog`                 | Known permission names with EN/SI labels, scope kind (organization, unit/geography, project), allowed sources and a **risk class**. Reference data, not authority. A permission with no explicit class is treated as **high** (fail closed). Provisional classes are labelled provisional until DEC-02. |
| `iam.person`                             | Staff identity per organization, separate from `authn.account` (new nullable `person_id` on the account), from farmers and from contact-only coordinators. A contact record never confers access.                                                                                                       |
| `iam.role` / `iam.role_version`          | Organization-scoped role with EN/SI names. **Role versions are immutable**: a version lists its permissions, coverage kind and source. Editing a role creates a new version; nothing already bound changes silently.                                                                                    |
| `iam.role_binding`                       | Person/account ↔ role version with scope (organization, unit, geography and/or project, intersecting as today, never OR), validity window, status, version, who requested and who approved. Pinned to a role version; moving to a new version is an explicit, approved action.                          |
| `iam.access_request` / `access_approval` | Proposed bind, unbind, version move, temporary or emergency grant. The risk class is computed from the catalog **at request time and is immutable**; reclassifying requires its own approval. One approval row per approver, unique per request.                                                        |
| `iam.access_audit` (append-only)         | Actor, session, action, before/after identifiers, request and approval ids, reason. Written atomically with the change; runtime logins cannot read it directly.                                                                                                                                         |

New `NOLOGIN` function owner `agri_iam_owner` (never an API login, never a member of a runtime role); the startup privilege gate gains the new identity and the private tables, exactly as for enrollment.

### 3. Authority and delegation rules (enforced in PostgreSQL, not in the UI)

- Administration capabilities are ordinary catalog permissions evaluated by the same predicates: `role.create`, `role.update`, `permission.grant`, `user.role.assign`, `device.view`, `device.approve`, `device.revoke`, plus read permissions for the admin views.
- **No self-grant:** an account cannot create, approve or apply an access request that targets itself.
- **No overflow:** a grantor can bind a role only if every permission in it is within the grantor's own current effective permissions at an equal or wider scope, and the target scope lies within the grantor's `permission.grant` scope. Checked inside the transaction after locks.
- **Risk-based approval (provisional Q62):** routine requests may be applied by one authorized administrator. High-risk requests need **two distinct approvers**, both different from the requester and from the grantee, each holding the approval permission for that scope. Open question: whether the requester may be one of the two.
- **Temporary and emergency grants (Q63):** a temporary binding must carry `expires_at`; expiry takes effect through the existing predicates immediately. Emergency elevation needs justification, a short maximum lifetime, enhanced audit and an automatic follow-up independent review. Whether emergency may skip dual approval is **not assumed** (needs separate authorization).
- **Step-up MFA (Q66):** high-risk apply requires a fresh proof of a consumed TOTP counter bound to the session and purpose with a short expiry (reusing the existing counter-consumption function). The current rule that every pilot staff account uses MFA is **not weakened** (conflict SC-06).

### 4. Mutation contract

Every mutation is a fixed function: stable mutation UUID, HMAC of the canonical payload for replay (same id, different payload conflicts), optimistic `expected_version`, current-actor and scope re-validation **after** advisory and row locks, atomic audit and materialization in one transaction, and a deliberately generic error to non-authorized callers. Runtime logins get `EXECUTE` only and read-only RLS views scoped by explicit read permissions; no direct writes.

### 5. Staff lifecycle (Q64)

One staff identity persists across transfers: a transfer ends the old bindings (history retained), creates new ones through the normal requests, revokes server sessions as required and records the actor. Deactivation revokes sessions and devices through the existing revocation functions. Offline limits (cached vault access cannot be remotely revoked) stay disclosed, not solved here. No public self-registration; accounts are provisioned by an authorized administrator.

### 6. Bootstrap (the first administrator)

No role, binding or grant is seeded. The first administrator is provisioned out of band by an operator script that calls an owner-only function with audit, in the style of the existing device-enrollment tool, under a documented two-person custody procedure. The procedure and who may perform it are an owner decision (DEC-02, DEC-08).

### 7. API, BFF and UI

Administrator-source routes only (never exposed by the field BFF): list/read roles, versions, permissions and bindings within scope; create role; create version; request bind/unbind/version move; approve/reject; apply. Strict DTOs, CSRF, response binding, no browser-supplied actor, source or risk class. English/Sinhala screens on the existing online-draft boundary (fresh authorized read, reviewed version, explicit review, one fixed retry request, no browser persistence). Names of roles are data, never hardcoded.

### 9. Acceptance tests (mutation-checked where they assert isolation or integrity)

Direct-SQL and API denial by default; missing, forged and spoofed actor/source; wrong organization; no self-grant, no overflow above the grantor's own scope, no approval by the requester, grantee or a duplicate approver; risk class cannot be changed to dodge approval; role version pinning and explicit moves; materialized grants match the role/scope exactly and revoke/expiry make the existing predicates deny immediately; replay and changed-payload conflict; stale version; authorization re-checked after lock waits; audit rolled back with the change; legacy direct grants unchanged; Officer A/B isolation with role-derived grants; wrong-organization foreign keys rejected; English and Sinhala flows, keyboard and late-response cancellation.

### 10. Required before implementation

1. **G1 independent security review** of this design (privileged grants, delegation ceiling, materialization, bootstrap).
2. Owner decisions under DEC-02: risk classification of each permission, number and independence of approvers, whether emergency may skip dual approval, who may create roles, bootstrap custody, maximum temporary lifetimes, MFA step-up scope.
3. Confirmation that role and permission names stay configurable data and that no job title carries implicit authority.

## Consequences and risks

- Materialization keeps today's tested predicates, at the cost of a derived-data consistency requirement (binding rows and materialized rows must change in one transaction under a lock; reconciliation tests and a verification function are part of P1-03b).
- Role version pinning avoids silent privilege escalation but means role changes need an explicit migration of bindings.
- A permission mistakenly left unclassified is treated as high risk, which may slow administration but fails safe.
- Without client DEC-02 input, all risk classes and approver counts remain provisional defaults and must be labelled so in the UI.

## 11. Security review notes (internal engineering review, 17 Nov 2026 — NOT the independent Gate G1 review)

This section records an engineer's threat pass over sections 1–10. It found design gaps, all addressed below as **binding requirements for implementation** (the earlier sections are not rewritten, so the review trail stays visible). It is not independent, it does not satisfy G1, and a reviewer outside the implementation team must still examine the design.

| #   | Threat (STRIDE)                                                                                                                       | Gap in the original text                                                         | Requirement added                                                                                                                                                                                                                                                                                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Tampering / time-of-check-to-time-of-use:** a request is approved, then its payload or scope is changed before it is applied        | Approvals were not tied to the exact content approved                            | Requests are **immutable once created**. Each approval stores the request's payload digest. Applying recomputes the digest after locks and refuses any mismatch. Any change is a new request with new approvals.                                                                                                                                                                 |
| 2   | **Spoofing / collusion:** two approvers who are really one human with two accounts, or an approver who is also the grantee's manager  | "Two distinct approvers" meant two accounts                                      | Distinctness is checked on the **person**, not the account (`iam.person`), and an approver may not be the grantee, the requester, or hold a binding created by the requester within a configurable window. Residual risk (real-world collusion) is disclosed, not claimed solved.                                                                                                |
| 3   | **Elevation of privilege via scope containment error:** a grantor binds at a scope they only appear to cover (unit hierarchy, cycles) | "Within the grantor's scope" was not defined for the unit tree                   | Containment uses the **same locked lineage evaluation** as the existing predicates (organization boundary first, cycle detection fails closed). Cross-organization binding is always refused. Tests include sibling units, a parent grantor, a child grantor, and a cyclic hierarchy.                                                                                            |
| 4   | **Elevation of privilege via role edit:** editing a role silently widens everyone bound to it                                         | Covered by version pinning, but role-version creation itself was not constrained | New versions never alter bindings. Moving a binding to a version that **adds** permissions is evaluated as granting each added permission (risk class of the highest added permission). Removing permissions applies immediately and needs only routine approval (fail-safe direction).                                                                                          |
| 5   | **Tampering with the permission catalog** to mark a dangerous permission routine                                                      | The catalog was reference data with no stated change control                     | Catalog rows are written only by the IAM owner function, versioned and audited. Lowering a risk class is a **high-risk change** needing the same two-person approval; raising is routine. Requests keep the class computed at creation (section 3).                                                                                                                              |
| 6   | **Drift between bindings and materialized grants** (a crash, a manual edit, a failed expiry)                                          | Consistency was asserted, not detected                                           | A **verification function** compares the expected grant set for every active binding with the actual `origin='role_binding'` rows and reports extras and missing rows; it runs in tests, in a scheduled monitor and before releases. Materialization and binding changes commit in one transaction under a per-account lock.                                                     |
| 7   | **Direct writes that bypass the workflow** (an operator or compromised runtime inserting grants)                                      | Only runtime logins were addressed                                               | Runtime logins hold no write privilege on grant tables (tested). `direct` grant insertion by an operator remains possible and is therefore **audited by a trigger** that records every insert, update and delete on grant tables regardless of origin. Operators with superuser access are out of scope for in-database prevention; this is a process control (custody, DEC-08). |
| 8   | **Repudiation / audit tampering**                                                                                                     | The audit table was "append-only" by intent                                      | No `UPDATE`/`DELETE` privilege for any application role, triggers reject them for everyone but a separate retention function, and audit rows reference the request and approval digests. Audit reads need their own permission and are themselves audited.                                                                                                                       |
| 9   | **Information disclosure:** listing roles, bindings or people reveals staff structure or confirms account names                       | Read scoping was not specified per list                                          | Every list is filtered **in the database** by an explicit read permission and scope. Responses use display names and opaque ids only, never login names or contact data. Not-found and not-permitted are indistinguishable.                                                                                                                                                      |
| 10  | **Step-up proof replay** or reuse for a different request                                                                             | A "fresh proof" was described without binding                                    | A step-up proof is **single use**, expires in minutes, and is bound to the session and the request's payload digest. Reusing it for another request fails.                                                                                                                                                                                                                       |
| 11  | **Emergency elevation abuse**                                                                                                         | Maximum lifetime and review were open                                            | Emergency grants require a justification, a short configurable maximum, automatic expiry that does not depend on a person remembering, an alert and a mandatory independent review record. Skipping dual approval stays **disallowed** until the owner separately authorizes it.                                                                                                 |
| 12  | **Bootstrap compromise** (the first administrator is the highest-value target)                                                        | Procedure was left to the owner                                                  | The bootstrap function works **once**: it refuses to run when any binding exists, requires two custodians in the procedure, writes an audit row with the operator identity and is removed from the deployed role set after use. Details stay an owner decision.                                                                                                                  |
| 13  | **Denial of service / lock contention** from evaluating grants or lineage on every call                                               | Not discussed                                                                    | Reuse of existing predicates keeps current cost. New read lists are bounded and keyset-paged; materialization takes a per-account lock only. A load test is part of P1-03b before real use (capacity is unmeasured today).                                                                                                                                                       |
| 14  | **Offline and cached authority:** a revoked staff member's device still shows cached screens                                          | Disclosed, not specified                                                         | Server reauthorization on every sync and command is the only authority; the UI states the limit. Revocation also revokes server sessions and device approvals in the same transaction.                                                                                                                                                                                           |

**Net effect on slicing and gates:** P1-03a (read-only catalog, person and role tables) is safe to start once the owner accepts the requirements above and a reviewer is arranged; P1-03b and P1-03c must include the tests for rows 1, 2, 3, 6, 7, 8 and 10 as acceptance criteria. All severity assessments are the engineer's and carry no approval.

## Addendum (19 Nov 2026, owner direction): permissions are database rows referenced by permission id

Status: **proposed, not implemented, not approved.** No migration, grant, role or authorization code accompanies it. It extends the permission catalog above and needs the same review (Gate G1) and the DEC-02 answers before any migration is written.

**Owner direction:** permission is handled in the database layer, as a permission id.

**What exists today (verified in the migrations):** grants store the permission as free text (`authz.permission_grant.permission`, `authz.project_permission_grant.permission`), and the predicates compare strings. There is no permission table and no permission id.

**Proposal:**

1. `iam.permission_catalog` rows get a stable `permission_id` (uuid, never reused) beside a unique `code`. The id is the identity; the code, labels and risk class are data that can be corrected without touching grants.
2. Grants and materialized role bindings reference the catalog by `permission_id` (foreign key). The text column stays during a transition, a constraint requires the two to agree, and the predicates move to the id in a reviewed migration. Unknown or retired ids are denied (fail closed).
3. An `iam.ui_action` catalog maps each screen action key (for example the withdraw button) to one `permission_id`, with EN/SI labels. Which button needs which permission is therefore data in the database, not a list in the front end.
4. A read-only capabilities function returns, for the signed transaction actor only, an explicit state for every known permission: `held` (a predicate returned true somewhere in the actor's scope), `not_held` (a confirmed denial: the enumeration finished and every candidate was false) or `unknown` (an error, limit or deadline stopped the evaluation; never a denial). It decides by calling the existing predicates, never by re-implementing them, and its candidate enumeration is a provable superset of every scope a predicate can accept. The BFF validates and passes it through. `held` is an account-wide action-discovery hint only: scope choices and final mutations are checked independently by the database. Answers live at most 60 s (provisional) with a hard cutoff. The full proposed contract (revision 2) is in [CAPABILITIES_ENDPOINT_CONTRACT.md](../security/CAPABILITIES_ENDPOINT_CONTRACT.md); it is **proposed, not approved**.
5. Unchanged: PostgreSQL decides every request. The list is a convenience for the interface; a missing or stale list never grants anything, and every mutation still re-checks inside its transaction.

**Defect found while preparing the contract (fixed in code, 19 Nov 2026):** the UI registry used `enrollment.policy.set`, which is only an audit-journal action name; the permission the predicate checks is `enrollment.policy`.

**Front end today:** `PermissionAction` is keyed by the permission code and accepts the server's per-record flags. When the catalog and the capabilities function exist, the key becomes the permission id (or the UI action key) and nothing else in the screens changes.

**Open for the owner / reviewer:** whether both the id and the code stay in grant rows after the transition; who may edit `ui_action` rows (proposed: the IAM owner function only, audited, like the catalog); whether retired permissions keep their ids for history (proposed: yes).

**Revision 2 (19 Nov 2026, after the owner's review of PR #106).** The architectural direction is accepted for further design. This is **not** Gate G1 approval and **not** authorization to implement C1, C2 or C3. Applied: the interface distinguishes confirmed denial, incomplete evaluation and service failure and uses a restricted, recoverable view on service failure (it no longer shows every action); the 60 s lifetime is a hard cutoff that client stale time cannot extend; `held` is a hint only; the 200-candidate and 2 s limits are provisional and gain a bounded total evaluation budget and a benchmark requirement; capabilities reads emit privacy-safe operational telemetry; cross-tab invalidation reuses the existing broadcast channel with regression tests (the existing channel carries vault suspension, not online sign-out); the field app may use capabilities for online UI only, never offline authorization. A predicate error can no longer become a denial, and the contract now argues and tests that candidate enumeration covers inherited and organization-wide grants. Endpoint anti-bot, concurrency, budget and load-abuse requirements join the SEC-04 workstream. C1 and C2 remain behind independent Gate G1 review; C3 behind a reviewed and tested C2. No grant, role, migration or privileged IAM mutation is part of this revision.
