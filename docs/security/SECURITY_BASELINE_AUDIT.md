# Security baseline audit and prioritized remediation plan (SEC-AUDIT-01)

Status: **audit and plan for owner and independent security review.** Written 19 Nov 2026 from a read of the repository at `main` (after PR #106). It is a code and configuration review plus the existing test evidence. It is **not** a penetration test, a load test or a production assessment, and nothing here is claimed to be production-proven. Companion: [threat model](THREAT_MODEL_AUTOMATED_THREATS.md).

How to read it: every statement about the system carries a `file:line` reference so a reviewer can check it. "Existing" means the control is implemented and tested in the repository; "Partial" means implemented with a stated limit; "Missing" means no implementation was found (a search that returned nothing is recorded as such, not assumed).

Severity scale used for this plan:

| Level  | Meaning                                                                                             |
| ------ | --------------------------------------------------------------------------------------------------- |
| **P0** | Release-blocking for any pilot that uses real farmer data or is reachable from the public internet. |
| **P1** | Needed before general production use; compensating controls may allow a limited pilot.              |
| **P2** | Hardening and hygiene.                                                                              |

All severities are the engineer's judgement and carry no approval.

## 1. What is already strong (preserve it)

These are accepted mechanisms; the plan builds on them and rewrites none of them.

- **Authentication stack.** Argon2id with parameter checks (`apps/api/src/authentication/passwords.ts:28`); a real Argon2id dummy hash so unknown accounts cost the same work (`login-coordinator.ts:40`); TOTP secrets stored encrypted, with replay protection through a consumed counter (`postgres-mfa-verifier.ts:60`); approved-device proof with constant-time comparison (`device-proof.ts:128`); database-held sessions with idle and absolute expiry; HttpOnly `__Host-` session cookie (`packages/auth-bff/src/index.ts:103`).
- **BFF boundary.** Browser never holds tokens; a route allow-list; non-GET requests must carry the exact public `Origin` and cross-site fetches are refused (`index.ts:355`); administrator-only routes are absent from the field BFF (`index.ts:346`); responses are re-validated and `no-store`; request URLs are capped at 2048 characters (`index.ts:117`, `304`) and bodies at 16 KB, with a larger cap for geometry (`index.ts:114-116`).
- **API hardening.** Trust-proxy off (`apps/api/src/security/http-hardening.ts:91`); no CORS in production; JSON-only, size-capped bodies; request and header timeouts; a cap on concurrent requests that sheds load with 503 (`http-hardening.ts:107`); strict headers.
- **Database authority.** FORCE row-level security, fixed `SECURITY DEFINER` functions, restricted runtime logins that the API refuses to use if they are over-privileged (`apps/api/src/pilot/runtime.ts:168-185`), verified TLS required in production (`runtime.ts:155`), HMAC-keyed idempotency journals, atomic audit.
- **Throttle foundation (SEC-04, partly implemented).** Two PostgreSQL buckets, per account and per client, keyed by HMAC; client identity only through a configured trusted hop count (`index.ts:90`); an unattributed bucket otherwise. Numbers are placeholders pending measurement ([decision brief](LOGIN_THROTTLE_DECISION_BRIEF.md)).
- **Bounded reads.** Cursor pagination with caps of 100 rows (`packages/validation/src/farmer-registry.ts:27`, `project.ts:14`, `enrollment.ts:21`), land viewport limited to 200 polygons and a 5° span with the stated intent that "a bulk export is not a viewport" (`packages/validation/src/land.ts:153`), 5000-vertex polygon cap, 160 KB geometry body cap, and no total counts or NIC search.
- **Supply chain and CI.** Dependency audit (a single, time-boxed exemption expiring 2026-12-15), CodeQL, lint, tests, structure check, independent browser QA.
- **Local infrastructure.** The development database is bound to localhost only (`infrastructure/compose.yaml:10`).

## 4. Prioritized plan: independent, small, reviewable slices

Each slice is its own PR with tests, a threat-model update, a runbook note and a handover row. **None changes privileged IAM, bypasses RLS, or marks any gate complete.** Slices marked _decision_ do not start before the named decision.

| Order | Slice                                                        | Closes           | Content                                                                                                                                                                                                                                                                                                           | Depends on                                   |
| ----- | ------------------------------------------------------------ | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 1     | **SEC-A1 Production configuration fail-fast**                | F-01             | In production the BFF and API must refuse to start (not answer 503 later) unless the proxy hop count is **explicitly** set, origins are HTTPS, the internal key is strong, and values are in range; one shared checker used by both apps; tests with mutation checks. Preserves current behaviour in development. | Directive Task 2 (authorizes it)             |
| 2     | **SEC-A2 Security events**                                   | F-04             | A small, dependency-free structured event emitter with a fixed event catalogue and an allow-list of fields (no secrets, factors, session material, farmer data, names or raw addresses), redaction tests, and emission from the BFF and API at the points listed in the threat model.                             | None                                         |
| 3     | **SEC-A3 Topology requirements and origin protection**       | F-02, F-03       | Provider-neutral deployment requirements and a verification checklist; an optional shared-secret "edge attestation" so an origin accepts only edge-forwarded traffic; deployment-topology tests with forged headers. Design as an ADR first.                                                                      | Hosting (OPS-04) for the final configuration |
| 4     | **SEC-A4 Budgets and limits table**                          | F-03, F-07, F-12 | One documented budget per route class (reads, writes, expensive reads, geometry writes, sync), BFF concurrency limit, header-size limits, and a route inventory with a test that fails when a route has no budget.                                                                                                | A2                                           |
| 5     | **SEC-A5 Progressive response and lockout-abuse protection** | F-05             | Design options with the measured trade-offs, then a reviewed migration. _Decision:_ D2, D3.                                                                                                                                                                                                                       | Owner decisions; load measurements           |
| 6     | **SEC-A6 Database resource guards**                          | F-06, F-08       | Measured role-level `lock_timeout`, idle-in-transaction timeout and connection limits; predicate cost measurements; reviewed migration.                                                                                                                                                                           | Disposable load stack; migration review      |
| 7     | **SEC-A7 Alerts, metrics and runbooks**                      | F-04, F-14       | Alert rules over the A2 events, thresholds marked provisional, and incident procedures for containment, recovery and evidence preservation.                                                                                                                                                                       | A2                                           |
| 8     | **SEC-A8 Adversarial suite**                                 | F-11             | Header spoofing, replay, spraying, limiter exhaustion, shared NAT, concurrency, expensive GIS, sync retries, control failure modes; mutation checks.                                                                                                                                                              | A1 to A4                                     |

**Capabilities endpoint (revision 2 of the contract).** Slices SEC-A4 and SEC-A8 also carry the endpoint's protections: a dedicated route-class budget and concurrency limit with single-flight per session, a total evaluation budget and deadline, fail-closed behaviour when a control is unavailable, jittered client backoff, and load-abuse tests (one session, many sessions, a concurrent hierarchy writer, a retry storm, limiter outage, header spoofing). See the contract, section 13. These are requirements for accepting slice C2, not approvals.

Slices 1, 2 and 9 are independent of every open decision and can start immediately. Slices 3 to 8 are designed first and implemented after their dependency is cleared.

**Authorized load and penetration testing** are release gates, not part of any slice: they need a written scope, a disposable environment with synthetic data only, an authorized tester and your approval. Until they are done, no control here is described as production-proven.

## 6. What this audit does not claim

It does not claim the controls are production-proven, does not measure any limit, does not test the live deployment, and does not replace independent review. Synthetic tests prove behaviour in the test environment only. A production release additionally needs validated infrastructure, named incident-response ownership, approved risk decisions, recovery procedures and an independent security review.
